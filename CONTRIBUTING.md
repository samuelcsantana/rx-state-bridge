# Contributing to rx-state-bridge

## Branching

This repo uses **GitHub Flow** — one long-lived branch (`main`), everything else is short-lived:

1. Branch off `main`, naming it after what it does: `feat/with-throttled-loading`, `fix/smooth-loading-timer-leak`, `docs/readme-badges`.
2. Open a PR into `main`.
3. Once approved and merged, the branch is deleted.

No `feature/`, `bugfix/`, `hotfix/`, or `release/` prefixes, and no direct commits to `main`.

## Commit messages

Follow [Conventional Commits](https://www.conventionalcommits.org/):

- `feat:` a new feature
- `fix:` a bug fix
- `refactor:` a code change that neither fixes a bug nor adds a feature
- `docs:` documentation only
- `test:` adding or correcting tests
- `chore:` build process, dependencies, tooling

This keeps `git log` scannable — it does not by itself drive the version number (see below).

## Adding a changeset

Versioning and the changelog are generated by [Changesets](https://github.com/changesets/changesets), not by parsing commit messages. If your PR changes the published package's behavior (anything under `src/`), add a changeset before requesting review:

```bash
npx changeset
```

Pick the bump type (`patch` for fixes, `minor` for new backwards-compatible operators/options, `major` for breaking changes) and write a one-line summary — it becomes the `CHANGELOG.md` entry. Commit the generated `.changeset/*.md` file with your PR.

Docs-only or test-only PRs don't need a changeset.

## What happens after merge

The `Release` GitHub Actions workflow opens (or updates) a `chore: version packages` PR that bumps `package.json` and compiles `CHANGELOG.md` from the pending changesets. Merging that PR runs `npm publish` automatically.

## Before opening a PR

```bash
npm run lint       # eslint + prettier --check
npm run typecheck  # tsc --noEmit
npm run test       # vitest
npm run build      # tsup — ESM + CJS + .d.ts
```

All of the above run in CI on every PR; make sure they pass locally first.
